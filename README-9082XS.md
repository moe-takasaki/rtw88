# 9082XS port status

This branch starts from Igor Listopad's RTL8189ES `rtw88` work, PR #465 head `475584a581cb449a8616e0339ecb85bcb88c67aa`. The target device is SDIO `02e7:9082`, exposed by Lunar as `mmc2:0001:1`.

The first patch adds a separate `rtw_9082xs` SDIO module and maps its WLAN register window to `0x14000` instead of RTL8189ES's `0x10000`. Six read-only register comparisons on hardware showed that the old window returns `0xea`, while the new window returns live register values. Other SDIO address spaces are left unchanged. The module builds against Lunar `6.18.41-lunar`.

9082XS has its own chip description and MAC table. Initial comparison showed 91 of 92 shared byte values matched Igor's table after bit reversal, but the vendor table also has 40 byte addresses absent from Igor's and uses mixed 8-, 16- and 32-bit writes. The driver now replays all 49 recovered MAC write operations in their original order and width. A mechanical comparison against the diagnostic table confirmed exact agreement. Hardware readback after that diagnostic table confirmed `0x4026=0x82`, `0x4027=0xac`, and `0x4421=0xf0`. The new table has not run through `rtw88` probe; runtime register access still needs separate validation.

The 9082XS chip description has its own power-on sequence. The SDIO transport now runs the same checked CMD52/CMD53 operations as the diagnostic module, including the final `0x4004` and `0x4100` enables. The RTL8188E revision register is not read before 9082XS power-on; a fixed single-RF-path description is used for this variant. The shutdown path now replays the vendor-derived preamble, low-power table, MCU stop, close table and final `0x401c=0x70`. This path builds but is not yet validated on hardware; generic register writes do not propagate SDIO errors to the caller.

The chip requests the privately installed `tilk/9082xs-nic.bin` instead of Igor's RTL8188E firmware. The loader treats it as a raw image without a legacy 32-byte header, selects its 4 KiB pages through register `0x82`, and checks each SDIO page transfer for errors. On 26 November, a staged `rtw88` probe reached eFuse parsing after the firmware download without SDIO errors. That run followed a successful diagnostic stage-2 probe, so a clean-boot `rtw88` result is still needed. The image itself is absent from this repository.

The 9082XS physical eFuse reader uses byte-width SDIO register accesses and bit-reverses the address byte, matching the diagnostic path that decoded 17 records and a valid MAC on hardware. The staged `rtw88` probe accepted logical ID `0x9082` but decoded an invalid MAC. The reader and logical-map decoder now preserve empty extended headers and continue reading the physical region; this correction builds but has not yet been retested on hardware.

The AGC table is now variant-specific: 130 raw 32-bit writes with the vendor's one-microsecond spacing, including the final two writes to `0x4c50`. The RF table also has its own 92 raw 32-bit writes to `0x4840`, with the vendor's one-microsecond spacing and two 100-millisecond pauses. Local entry-by-entry comparisons matched the diagnostic tables. PHY remains separate work; neither table has run through `rtw88` on hardware.

Initialization is guarded by `experimental_hw_init=0` by default. With `experimental_hw_init=1`, the current branch deliberately stops after eFuse setup and returns `-EOPNOTSUPP` before interface registration or PHY/RF configuration. Runtime register access, PHY, radio calibration and shutdown are incomplete. The diagnostic module in `../experimental/` has independently completed chip power, firmware download, MAC table replay and eFuse decode on the target.

Next: restore access to the box, verify the corrected eFuse MAC and shutdown path on a clean boot, validate runtime register bit order, and adapt PHY tables and board calibration. Then extend staged probe through interface registration and traffic. Keep the extracted firmware outside the repository until redistribution rights are established.
