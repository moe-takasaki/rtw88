# 9082XS port status

This branch starts from Igor Listopad's RTL8189ES `rtw88` work, PR #465 head `475584a581cb449a8616e0339ecb85bcb88c67aa`. The target device is SDIO `02e7:9082`, exposed by Lunar as `mmc2:0001:1`.

The first patch adds a separate `rtw_9082xs` SDIO module and maps its WLAN register window to `0x14000` instead of RTL8189ES's `0x10000`. Six read-only register comparisons on hardware showed that the old window returns `0xea`, while the new window returns live register values. Other SDIO address spaces are left unchanged. The module builds against Lunar `6.18.41-lunar`.

9082XS has its own chip description and MAC table. Initial comparison showed 91 of 92 shared byte values matched Igor's table after bit reversal, but the vendor table also has 40 byte addresses absent from Igor's and uses mixed 8-, 16- and 32-bit writes. The driver now replays all 49 recovered MAC write operations in their original order and width. A mechanical comparison against the diagnostic table confirmed exact agreement. Hardware readback after that diagnostic table confirmed `0x4026=0x82`, `0x4027=0xac`, and `0x4421=0xf0`. The new table also completed in the opt-in `rtw88` staged probe; runtime MAC behavior still needs validation.

The 9082XS chip description has its own power-on sequence. The SDIO transport now runs the same checked CMD52/CMD53 operations as the diagnostic module, including the final `0x4004` and `0x4100` enables. The RTL8188E revision register is not read before 9082XS power-on; a fixed single-RF-path description is used for this variant. The shutdown path now replays the vendor-derived preamble, low-power table, MCU stop, close table and final `0x401c=0x70`. A staged hardware probe returned through cleanup without an SDIO error, but shutdown register effects have not yet been read back; the generic register operations return no error directly. A first-error latch now catches SDIO transfer failures during staged initialization. The SDIO stop callback also skips interrupt-mask writes before an IRQ is claimed, avoiding the previously observed failed write to local address `0x14` during early probe cleanup.

The chip requests the privately installed `tilk/9082xs-nic.bin` instead of Igor's RTL8188E firmware. The loader treats it as a raw image without a legacy 32-byte header, selects its 4 KiB pages through register `0x82`, and checks each SDIO page transfer for errors. On 26 November, a staged `rtw88` probe after a box power cycle downloaded firmware without SDIO errors. The image itself is absent from this repository.

The 9082XS physical eFuse reader uses byte-width SDIO register accesses and bit-reverses the address byte, matching the diagnostic path that decoded 17 records and a valid MAC on hardware. The reader and logical-map decoder preserve empty extended headers and continue reading the physical region. The variant reads eFuse before downloading firmware, matching the diagnostic sequence. A staged hardware probe after the box power cycle decoded logical ID `0x9082` and MAC `b4:04:18:4d:50:82` without falling back to a random address.

The PHY table is now variant-specific: 284 ordered 32-bit operations, including bit-reversed and raw masked writes, each followed by the vendor's one-microsecond delay. A local entry-by-entry comparison matched the diagnostic table, and the changed module built against Lunar `6.18.41-lunar`. The AGC table has 130 raw 32-bit writes with the vendor's one-microsecond spacing, including the final two writes to `0x4c50`. The RF table has 92 raw 32-bit writes to `0x4840`, with the vendor's one-microsecond spacing and two 100-millisecond pauses. Both the checked diagnostic module and an opt-in staged `rtw88` probe completed MAC, PHY, AGC and RF table replay on the box without logged SDIO errors. This verifies transport and table replay, not calibration, receive, transmit or Wi-Fi operation.

Initialization is guarded by `experimental_hw_init=0` by default. With `experimental_hw_init=1`, the branch reads eFuse and downloads firmware, then deliberately returns `-EOPNOTSUPP` before interface registration. Passing `s9082c_stage_radio_tables=1` to `rtw_8188e.ko` additionally replays the 9082XS MAC, PHY, AGC and RF tables while the chip is powered, checks the first SDIO register-access error after each table, and then returns through the same guard. The optional stage completed on hardware and all four modules unloaded cleanly. Radio calibration, receive, transmit and shutdown register effects remain unverified.

For a registration-only experiment, also pass `experimental_register_hw=1` to `rtw_9082xs.ko`. This opts out of the post-eFuse stop and registers the PHY, but does not bring the interface up. The 9082XS WLAN register window is inaccessible after the eFuse phase powers the chip off, so channel configuration and TX-power programming are deferred until power is on; interrupt-mask writes are skipped during removal if it is off. On a clean boot, two successive load/unload cycles registered `wlan0` with eFuse MAC `b4:04:18:4d:50:82`, kept it down, and logged no SDIO errors. A previous build without the TX-power guard produced repeated SDIO timeouts during regulatory notification and left the chip unable to re-probe until reboot. Interface start, calibration, receive and transmit are not yet validated.

`experimental_start_once=1` additionally runs `rtw_power_on()` and `rtw_power_off()` during probe after registration, with the interface still down. Two successive hardware runs completed this MAC/PHY/HCI initialization and shutdown without logged SDIO errors, and all modules unloaded. This checks the core power path but does not exercise the mac80211 start callback, periodic calibration or traffic.

A short `ip link set wlan0 up` / `down` run now exercises the mac80211 start and stop callbacks without an active Wi-Fi manager. The first run exposed two powered-off callback paths: asynchronous receive-filter configuration and interface removal, followed by a redundant power-off during stop after idle power save. The 9082XS path now caches filter state, skips those register writes while off, and avoids stopping an already powered-off chip. Two consecutive one-second up/down runs, the second with temporary diagnostics removed, returned success, left no SDIO errors, and unloaded all modules. This does not establish RF calibration, scan, association or packet traffic.

The latest build completed after BitBake recreated `Module.symvers`, and its staged table replay was retested on the box. The driver reported the expected eFuse MAC, completed MAC/PHY/AGC/RF table replay without an SDIO error, and stopped before interface registration. All four modules unloaded successfully and SDIO `02e7:9082` remained visible.

The vendor binary's `TDB_S9082_Init_PHY_PG` loads the same six rate-power entries as the inherited RTL8188E table after translating its `0x4e00`-series register addresses to `0xe00`-series `rtw88` offsets. Its 168 regulatory TX-power records contain all 143 inherited limit records with identical fields and values. The remaining 25 records explicitly specify index `63`, which is the default for missing limits in `rtw88`. The packed eFuse difference byte uses signed four-bit values; the board's `0xbf` decodes to low nibble `-1` and high nibble `-5`, as in the inherited little-endian layout. These comparisons validate table contents and parsing layout, not RF output power on hardware.

Passive scanning is now exercised with `wlan0` up. It completes without an SDIO transfer error but reports zero BSSs; the radio is not operational. An initial IRQ diagnostic found that writing the SDIO HIMR at local offset `0x14` read back zero. The vendor module addresses the 9082XS local window at `0x2000` and reverses the bits in each nibble of the interrupt mask, interrupt status and RX length fields. With those rules applied, a clean-boot hardware test read back the logical mask `0x40001`. During a passive scan, HISR read `0xc0800000` and logical RX length was zero; no IRQ callback or beacon was observed. The interface then went down and all four modules unloaded cleanly, with SDIO `02e7:9082` still present. This confirms the corrected local register access and shows the remaining problem is earlier in the receive path or its enable sequence. It does not establish that the receive FIFO handling works.

The vendor init sets logical CCK and OFDM enable bits 24 and 25 of BB register `0x4800` through a byte-bit-reversing BB accessor. The inherited RTL8188E runtime path wrote those bits directly; the 9082XS path now reverses them before writing. This variant-specific correction builds and an opt-in hardware run still completes interface up/down and passive scan without SDIO errors, but the scan reports zero BSSs. Readback of register `0x4800` was `0x00200000` through both CMD52 and CMD53; a temporary CMD52 byte write of the two physical enable bits also read back zero. The reason this register does not retain those bits is not yet known. The temporary diagnostic write and logs were removed. The vendor also performs IQ and LC calibration during interface initialization, while this branch still defers calibration until transmit preparation.

The vendor's RF serial write sends the same address/data command as `rtw88` through its bit-reversing BB accessor, and its serial read uses the bit-reversed PI selector and response. The 9082XS runtime RF accessors now apply those rules. The vendor's RF setup also enables the RF environment through that accessor: logical bit 4 at `0x4870`, and logical bits 20 and 4 at `0x4860`, correspond to physical bits 3, 19 and 3. The 9082XS RF setup now uses those physical masks while leaving the raw HSSI length-bit clears unchanged. Hardware completed probe, interface up/down and passive scan with these changes and no new SDIO errors, but the RF channel register still read zero and the scan remained empty. Reads of the two RF response registers were zero. During the scan, `0x860=0xf0fe800c` and `0x870=0xc000e000`. Sample PHY table readbacks matched direct writes at `0x880=0x0d003038` and `0x884=0x00000080`; table transport alone does not establish that the RF serial interface is operating.

The vendor's channel switch updates a cached RF register `0x18`; it does not use a fresh RF read. The last RF-table command targeting this register, physical `0x80012fe0`, decodes to logical `0x0f407`. The 9082XS path now seeds a register cache from that value after each RF table load and updates it on channel changes. This avoids replacing the table configuration with the zero returned by the current RF read path. The change built against Lunar `6.18.41-lunar`; a hardware passive scan and interface up/down completed with no logged SDIO errors, but the scan still returned zero BSSs. The cause of absent RF reception remains open.

The vendor also programs crystal capacitance in `0x4024` through its bit-reversing BB accessor. The inherited RTL8188E path used a raw mask. For the board's eFuse crystal value `0x11`, the raw register before correction was `0xaca288ff`, decoding to field `0x8a2` instead of the intended `0x451`. The 9082XS path now performs the masked update in logical BB bit order; on hardware the raw readback became the predicted `0xac4491ff`. Interface up/down and passive scan still completed without SDIO errors, but no BSS was received. The corrected capacitance field is verified; RF operation is not.

The same logical BB update now covers later CFO crystal adjustments. The vendor's optional PA-bias sequence changes the low nibble of `0x4016` through values `1` and `9`; the inherited RTL8188E sequence changes the high nibble. The 9082XS branch follows the vendor sequence when the eFuse flag enables it. This board's eFuse byte `0x1fa` is `0xff`, so that branch is skipped and cannot be validated here. After the change, the target build passed; `0x4024` still read `0xac4491ff`, interface up/down and passive scan completed, and the scan still found no BSS.

The 8051 firmware-ready bit was set during a scan (`0x4080=0xe0c00063`), and the receive filter maps were open. A monitor-mode interface on channel 1 stayed at zero RX packets over six seconds. This points to a problem before delivery to the station filter, although that short observation does not prove the RF path is silent on every channel. The vendor's eFuse IOL patch is conditional on a private IOL flag; its necessity on this board has not been established.

The vendor `ConfigPHY_BB9083X` enables `SYS_FUNC_EN` with `0x04c0`, writes `RF_CTRL=0xe0`, then writes the low `SYS_FUNC_EN` byte as `0xc7`. The inherited RTL8188E sequence left `RF_CTRL=0x07` and `SYS_FUNC_EN=0x3f03` during scans. With the exact 9082XS sequence, hardware read `SYS_FUNC_EN=0x3fc7`, `RF_CTRL=0xe0`, `REG_FPGA0_RFMOD=0xc1200000`, and nonzero RF responses; RF register `0x18` read `0x7c01`. The previous RF responses were zero and `REG_FPGA0_RFMOD` read `0x00200000`. Interface start, passive scan, stop and module removal remained error-free. The scan still reported zero BSSs, and monitor mode saw zero RX packets over five seconds each on channels 1, 6 and 11. This validates that the RF serial path now responds, while reception remains unverified.

The RF fix exposed the next problem: on channel 6, PHY CCK CRC OK counted frames while monitor RX remained zero and SDIO RX length stayed zero. Vendor `WMACSetting_init` sets `RCR=0x0e000673`; the original `rtw88` monitor path used `0xf000600f`. Vendor initialization also writes `0x20` to `REG_RX_DRVINFO_SZ` and `0x60` to `REG_RXDMA_AGG_PG_TH + 1`, versus the inherited `0x04` and `0x06`. Writing all three vendor values through debugfs produced 6 monitor RX packets in five seconds with no RX errors. In six five-second trials, omitting any one of these three yielded zero RX packets, while omitting the vendor control-filter map or FIFO boundary still yielded packets. The three required values are now in the 9082XS driver path. The rebuilt modules registered `wlan0` and received 2 monitor packets on channel 6 without manual writes. A passive station scan completed but still found zero BSSs, so scan filtering or dwell remains to be resolved. After a separate box reboot, a further scan-filter experiment was invalid because the chip failed power-on step 11 with SDIO `-84/-110`; a cold power cycle is needed before more hardware tests.

After a cold start, the integrated path received 9 monitor packets in five seconds on channel 6 and later 60 total without RX errors. Passive station scan restricted to 2437 MHz still returned zero BSSs. Clearing RCR bit 6 during a scan did not change that result; adding the inherited management and broadcast acceptance bits in monitor mode did not increase reception. Ghidra's 9082XS receive tasklet confirms a 24-byte descriptor, driver-info length in eight-byte units, and 128-byte aggregate alignment, matching the inherited SDIO parser. An RF read during the 2437 MHz scan reported channel 1, but the serial readback may be stale; the channel callback is now instrumented for the next test. A debugfs PHY-register read raced with idle power-off and timed out, after which power-on step 11 again failed. The 9082XS debugfs register accesses now check power state under the device mutex, and idle wakeup stops before touching the channel registers when power-on fails. These changes built against Lunar `6.18.41-lunar`; hardware retest awaits another cold start.

On the next cold start, channel callback logs confirmed a requested 2437 MHz scan programs RF18 for channel 6 and returns to channel 1 after about 124 ms. A 500-TU dwell and repeated scans still found no BSSs. Nearby 2.4 GHz access points were observed on channels 7 and 11; 1000-TU passive scans there also found none. A small packet-socket capture on the box received monitor frames on all three channels, but every captured frame was an 802.11 probe request (subtype 4), not a beacon (subtype 8). CCK CRC OK counters advanced; OFDM CRC errors rose with zero OK in several short channel-11 samples, although a later sample did show OFDM OK frames. Forcing vendor survey IGI values `0x1e` and `0x28`, and trying the vendor no-link beacon-control value during scans, did not find a BSS. A test bypassing inherited RTL8188E LNA/EDCCA adaptation also did not help and was reverted. The vendor initializes IQ and LC calibration before scanning, while this branch still defers calibration until transmit preparation; the missing calibration remains a candidate, not a proven cause.

An active scan returned no BSSs and exposed a separate power race: after scan completion, the queued SDIO TX worker read local free-page register `0x2020` three times after power-off, each timing out. The subsequent probe failed power-on step 11. The 9082XS SDIO stop path now cancels the TX worker and purges its queues before power-off. This builds against Lunar `6.18.41-lunar`, but requires a cold-start hardware retest.

After cold power removal, the same active scan completed with zero SDIO errors. Unloading and reloading all modules on that boot again registered `wlan0`, confirming the TX worker no longer poisons the chip during scan shutdown. Ghidra's vendor `hw_reg_9083x_set` clears physical RCR bit 0 on survey entry and sets it on completion. Forcing `RCR=0x0e000632` during a long passive scan immediately yielded 8 BSSs. The 9082XS scan path now masks bit 0 on start and on intermediate receive-filter writes, then restores the cached RCR on completion. With this code, a 1000-TU passive scan of channels 7 and 11 found 9 BSSs without debugfs writes. A normal passive scan across channels found 13 BSSs; after unloading and reloading the modules, it found 11. A normal active scan found 14. All scans returned success, and no SDIO errors appeared. These results establish discovery and RX of nearby access points; association and user data are still untested. The active scan result alone does not establish successful TX.

A temporary WPA2 test network exposed a blocked SDIO TX path: mac80211 submitted authentication frames, but `REG_SDIO_FREE_TXPG` always read zero, so no CMD53 write occurred. The vendor initialization reverses the bits of each byte before writing the queue-page allocation registers. Applying that rule to `REG_RQPN` made the free-page read nonzero; a subsequent integrated-driver diagnostic reported nibble-decoded `0x9209000c`, or 12 high, 9 low and 146 public pages. The inherited `rtw_is_8189es()` path already routes management frames to the high FIFO and uses 128-byte RX aggregation alignment for this SDIO variant. The access point then answered authentication requests and mac80211 logged `authenticated`. A later diagnostic recorded a 66-byte authentication frame and three 129-byte association frames sent to the high FIFO with CMD53 return code zero. No association response reached mac80211, which timed out. The vendor reads the free OQT register at SDIO local `0x25` with reversed nibbles; the variant now decodes that value in the inherited OQT check. The observed raw byte was `0x80`, or 16 free entries, so OQT was not the immediate association blocker. No WPA handshake or IP traffic has been established.

Next: determine why association responses are intermittent and why beacon reception stops after a successful association; then verify WPA and data transfer. Complete the 9082XS-specific IQ and LC calibration path and remove experimental initialization gates after validation. Keep the extracted firmware outside the repository until redistribution rights are established.

Further testing observed several successful association responses (`status=0`, AID 3) from the test AP without changing the driver or registers. The station then reported beacon loss and disconnected after about four seconds; no WPA handshake or IP traffic followed. Association remains intermittent. mac80211's `corrupt beacon` message means its IE parser marked a received beacon malformed, although 13 target beacons in a separate monitor capture had complete IE sequences. The captures alone do not identify the failing receive or transmit stage. A radio-frequency calibration trace found that the inherited RTL8188E LC path started with `RF18=0x0fc07` but restored `0x00c07`, losing upper configuration bits. The 9082XS branch now uses its cached RF18 value and restores all bits around LC calibration. The rebuilt driver logged `restore=0fc07` on hardware and still authenticated, but association timed out in the 30-second retest. This change fixes RF register preservation; it does not establish reliable association.

After another cold start, authentication still succeeded while association timed out. The 9082XS SDIO register path returned different values for byte and 32-bit reads of MACID and BSSID: writing six bytes made byte reads match the requested addresses, but a 32-bit read reversed bits in several bytes. Test builds writing BSSID as a 32-bit word, and both MACID and BSSID as words, changed the corresponding readbacks but did not improve association. A passive station scan received five target beacons with 219-byte frames and complete IE boundaries. A build that suppressed HT advertised capability sent a 127-byte association packet in one 128-byte SDIO transfer and still timed out, so crossing that transfer boundary is not required for the failure. Disabling driver LPS and testing the vendor's raw ACK timeout/retry values separately also did not establish association. All of these test-only source changes were removed.

The vendor `EDCA_init` writes `0x0850` to four SIFS registers that the inherited path does not initialize. A separate 9082XS test build added those writes; authentication still worked and association timed out on every observed attempt. Another test kept only RCR bit 0 clear (`0x0e000672`) outside scans, avoiding the extra bit 6 change in an earlier failed filter experiment. It likewise authenticated but did not establish association in a 30-second run. Both changes were reverted pending stronger evidence.

The reused RTL8188E IQ calibration wrote its direct BB constants in the wrong bit order for 9082XS and repeatedly reported neutral TX/RX coefficients (`0x100/0`). The 9082XS IQK path now reverses bits within each byte for direct BB constants, uses the chip's masked BB access convention, reads the TX Y result through that convention, and programs the two RF mode-table stages through BB port `0x840`. It applies TX/RX correction only after a selected calibration result. Hardware traces now show changing TX results such as `0x102/0x08` and successful RX shots; failed shots retry. A passive station scan still found the test AP with no SDIO errors. Authentication remained possible, but association still timed out in the 20-second test. Power tracking and sustained WPA/data operation remain unverified.

The generic rtw88 registration had also advertised `RX_INCLUDES_FCS`, causing mac80211 to trim four bytes from every received frame. A 9082XS beacon captured before mac80211 had a 219-byte length with its final IE ending exactly at byte 219: there was no FCS in that RX length. The 9082XS registration now omits this hardware flag. A target-channel passive scan still found the AP, and the following WPA attempts authenticated without any new `corrupt beacon` messages. Association continued to time out, so the remaining blocker is separate from the beacon IE truncation.

The 9082XS firmware has not delivered the TX report expected by the inherited RTL8188E path. The variant therefore no longer advertises `REPORTS_TX_ACK_STATUS` to mac80211 until its report format is understood. In a 30-second test, authentication continued and the repeated firmware TX-report timeout warning disappeared. Association still timed out; mac80211 retried requests sooner because it no longer waited for a reported ACK.

The vendor TX-descriptor routine gives management frames a software sequence number and an explicit six-attempt retry limit. The 9082XS TX path now copies the sequence number from the 802.11 header, leaves hardware sequence generation off, and encodes that retry limit instead of the inherited RTL8188E fallback limits. A temporary diagnostic confirmed increasing probe-request sequence numbers followed by distinct authentication and association sequence numbers. Authentication still completed; the AP did not answer the association attempts in the 30-second test. This change aligns the management descriptor with the vendor format but does not yet establish association.

The vendor hardware-register cases for station MAC and BSSID use 32-bit writes for the first four bytes. They write the final two MAC bytes directly, but bit-reverse the final two BSSID bytes before byte writes. The 9082XS port configuration now follows that sequence for ports 0 and 1. A 30-second hardware run still authenticated and timed out association, so this corrects the register access pattern without proving the remaining link path.
